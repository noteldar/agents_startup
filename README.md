Agent Startup Project Plan


Project Overview

Agent Startup is a multi-agent system designed to solve complex internet research tasks by leveraging four persistent AI agents working collaboratively. Each agent is implemented with PydanticAI (an LLM-based agent framework) and equipped with unique roles, memory, and tools to access the internet. By having multiple specialized agents cooperate, the system can tackle problems requiring deep thought and diverse skills, often achieving better results than a single agent alone
medium.com
. This approach harnesses the unique strengths of each agent and enables parallel problem-solving for improved efficiency
superannotate.com
. The core idea is to maintain a persistent memory (using a memory layer called mem0) that accumulates knowledge across sessions, and to facilitate structured communication protocols (one-on-one chats and team meetings) for agent collaboration. A designated CEO agent coordinates the team, breaking down high-level problems into sub-tasks and integrating results. The system also incorporates a reputation profile mechanism: agents give feedback scores to each other after one-on-one interactions, allowing the system to identify effective collaborations over time. In summary, Agent Startup is a centralized multi-agent framework – one agent acts as a hub to manage others – with robust memory and communication channels to collectively solve tasks
arxiv.org
.
Agents and Roles
The Agent Startup consists of four persistent AI agents, each with a unique name, role, and personality. All agents are implemented as PydanticAI Agent instances, meaning they are backed by LLMs and can use tools (like web search) and system prompts as defined in their configuration
ai.pydantic.dev
. They run continuously across sessions, retaining memories of past interactions and learning from them. The four agents and their primary roles are:
Agent 1 – "CEO" (Coordinator): The leader of the agent team, responsible for overall strategy and coordination. The CEO agent receives the high-level research problem and decomposes it into manageable sub-tasks. It assigns these tasks to the other agents based on their expertise, then later collects and integrates their findings. The CEO moderates all team meetings, ensuring each agent shares updates one at a time, and it adjusts the game plan as new information emerges. This agent acts as the central hub managing the others’ interactions
arxiv.org
. (Like all agents, the CEO has access to the internet and persistent memory, but its primary role is decision-making and orchestration.)
Agent 2 – "Researcher" (Information Specialist): A specialist in gathering information from the web. The Researcher agent excels at using the web_search tool to find data, articles, and evidence relevant to the task. It has a curious and thorough persona, ensuring no critical information is missed. When assigned a sub-task (e.g. investigating a specific question or scanning for sources), this agent queries the internet and reads through results. Everything it reads or discovers is stored to memory (mem0) for the team to recall later. The Researcher can initiate one-on-one chats with other agents to clarify what information is needed, and contributes its findings during meetings when prompted by the CEO.
Agent 3 – "Analyst" (Critical Thinker): The Analyst agent focuses on reasoning, analysis, and verification. It processes the information gathered (from the Researcher or other sources) and provides insights or conclusions. For example, if the task involves comparing options or interpreting complex data, the Analyst will break down the problem logically. It might cross-verify facts using the web or double-check claims to avoid errors. The Analyst often engages in one-on-one chats with the Researcher to discuss findings or with the Synthesizer to formulate coherent explanations. In meetings, the Analyst shares its reasoned perspective when the CEO calls on it, and it helps refine the overall solution by pointing out inconsistencies or knowledge gaps.
Agent 4 – "Synthesizer" (Communicator): The Synthesizer agent's role is to compile and present the knowledge gathered by the team. It specializes in synthesizing information into clear summaries, reports, or final answers. When sub-tasks are assigned, the Synthesizer might take interim outputs from the Researcher and Analyst and draft a cohesive narrative or recommendations. It has strong language and organizational skills (leveraging the LLM’s capabilities to produce well-structured text). The Synthesizer ensures that the final output of the project is comprehensive and understandable. It may chat one-on-one with the Analyst to ensure interpretations are correct, or ask the Researcher for additional details if something is unclear. During team meetings, the Synthesizer speaks up when asked to present a summary of progress or to propose a final solution based on all agents’ contributions.
Common Capabilities: All four agents share certain capabilities by virtue of the PydanticAI framework. They each have access to the internet via a web_search tool, allowing them to query online information in real-time. They also share the persistent memory (mem0), meaning anything one agent learns or says can later be accessed by others as context. Moreover, any agent can communicate with any other using the defined chat protocols. Despite having distinct primary roles, the agents are not rigid—each can perform general reasoning and assist in various ways, but their specialization helps divide the labor of complex tasks
superannotate.com
. This division of roles, combined with overlapping abilities, creates a robust team where agents support one another, reducing blind spots and increasing overall reliability

Tools and Resources
To perform their tasks, the agents in the system utilize a set of tools and resources integrated via PydanticAI:
Internet Search (web_search): A built-in tool that agents use to retrieve information from the internet. This functions like a search engine interface. An agent can query web_search with a prompt or keywords, and it will return search results or scraped content from web pages. The tool enables the Researcher (and others when needed) to gather current data, facts, and references from the web. For example, the Researcher might call web_search("latest statistics on climate change 2025") to find up-to-date info. The results can then be read and summarized by the agent. This internet access is crucial for abstract research tasks, ensuring the agents have a wide knowledge base beyond their initial training. All content retrieved via web_search is also saved into memory (tagged with source details) so it can be cited or re-checked by other agents later.
Persistent Memory (mem0): A global memory store that logs everything the agents read, say, or do. We use the mem0 memory management system to provide long-term, contextual memory for the agent startup. Mem0 is an architectural framework for persistent AI memory, allowing the system to maintain context across multiple interactions and sessions
medium.com
. Every piece of information an agent encounters (such as web content, chat messages, or meeting transcripts) is recorded in mem0. This means the agents effectively "remember" all details from earlier in the project, even if the session is paused or continued days later. Mem0's implementation includes both a vector database (for semantic search of past knowledge) and a structured store (for factual details and relationships)
medium.com
. The agents can query this memory to recall relevant past discussions or data; for instance, the Analyst might look up if a particular source was already found by the Researcher last week. Persistent memory greatly enhances the agents’ ability to build on prior knowledge and avoids repetitive work
medium.com
. (Without such memory, the agents would forget context between conversations, hindering complex problem-solving.)
Communication Channels: The system provides protocols for inter-agent communication: one-on-one chat channels and a group meeting channel (both described in the workflows below). These are not physical "tools" that agents call like functions, but rather built-in communication modes. The infrastructure allows any two agents to start a direct dialogue, and allows the CEO to convene all agents in a structured meeting. Under the hood, these channels ensure that messages are properly routed to the intended agent(s) and logged to memory. They also enforce limits (like the 30-message cap in 1-1 chats) to keep interactions concise. From an implementation perspective, one can think of these channels as specialized functions or methods each agent can invoke (e.g., initiate_chat(partner_agent_name)) and the system handles the rest.
LLM Reasoning and Other Tools: Each agent is essentially powered by an LLM (via PydanticAI), which means they inherently have abilities in natural language understanding, generation, and reasoning. While not an external tool, this capability is the backbone of their functioning—agents "think" and produce content by prompting their underlying LLM with the current context (including system instructions, memory, and recent messages). In PydanticAI, agents can also be extended with additional custom tools (e.g., a calculator, code executor, or domain-specific APIs) by defining functions that the LLM can call. For the initial scope of Agent Startup, we focus on the web search and memory, but the design allows plugging in more tools as needed. For example, if a research task required complex calculations, we could add a calculator tool that an agent (likely the Analyst) could use to ensure numerical accuracy.
By combining these tools and resources, the agents can search for information, remember and retrieve past knowledge, and communicate effectively. This setup provides a rich environment for the agents to operate in, closely resembling how a human research team might use the internet, take notes, and discuss findings in pursuit of an answer.
Workflows and Collaboration Protocols
To coordinate the actions of multiple agents, Agent Startup defines clear workflows for communication and task execution. These include protocols for one-on-one interactions, multi-agent meetings, and the overarching problem-solving process led by the CEO agent. The workflows ensure that agents collaborate in a structured manner, preventing chaos and keeping the project on track
medium.com
. Below, we detail each key workflow:
One-on-One Chat Protocol
Any two agents can engage in a private, focused conversation using the one-on-one chat protocol. This is useful when a pair of agents need to exchange information or ideas without involving the entire group (for example, the Researcher clarifying requirements with the CEO, or the Analyst debating a point with the Synthesizer). The one-on-one chat works as follows:
Chat Initiation: An agent can initiate a chat with another agent at any time (provided neither is currently in another chat or meeting). For instance, the Analyst might ping the Researcher for a quick discussion by calling the chat function with the Researcher’s identifier. The system then opens a dedicated private channel for these two agents.
Private Dialogue: Once the chat is opened, the two agents freely exchange messages back and forth. The content can be questions, answers, brainstorming ideas, or sharing data. This conversation is not visible to the other agents in real time, ensuring the pair can speak candidly or sort out details independently. However, all messages are still recorded in the global memory (mem0) with tags indicating the participants and chat session. For example, if the Researcher shares a web link or a piece of data in the chat, that information is stored and could later be referenced by others if relevant.
Message Limit: The chat is capped at 30 messages total (each message could be thought of as one agent's turn). This limit (which can be adjusted if needed) ensures the chat remains focused and doesn’t devolve into an endless exchange. It forces the agents to move to conclusions or escalate to a meeting if more discussion is needed beyond the 30-message window. The system will gently remind the agents as they approach the limit. In practice, 30 messages (15 per agent in a typical alternating scenario) is enough for a substantial interaction to solve a minor question or make a decision.
Chat Conclusion: The one-on-one session can conclude early if the issue is resolved. Either agent can explicitly end the chat, or it ends automatically once the 30-message cap is reached. At conclusion, the transcript of the conversation is finalized and saved to memory (if not already). The agents part ways from the channel, returning to an idle state or continuing their work on tasks.
Post-Chat Feedback: After a 1-1 chat, each agent privately rates the quality of the interaction with their partner on a scale of 1 to 10. This rating reflects how helpful, clear, and cooperative the other agent was during the exchange. For example, the Researcher might rate the Analyst a 9 if the Analyst’s questions were insightful and helped clarify the research direction, while the Analyst might rate the Researcher an 8 if the answers were useful but perhaps a bit delayed. These scores are then logged in each agent’s reputation profile. (See the Memory and Reputation System section for how these scores are stored and used.) The rating process is quick and does not involve additional dialogue—it's more of an internal feedback that each agent provides to the system.
All one-on-one chats contribute to building rapport and understanding between agents. Initially, the system may encourage some random pairings in 1-1 chats (e.g., pairing agents arbitrarily) so that every agent gets to interact with every other and share knowledge widely. Over time, as reputation data accumulates, the system can prioritize pairing agents who have shown strong synergy or high mutual ratings. This adaptive pairing strategy means early conversations are exploratory, while later ones are optimized for effective collaboration. By structuring 1-1 chats with clear start and end conditions and incorporating feedback, Agent Startup ensures that these private dialogues remain productive and feed into the overall knowledge base and team dynamics.
Team Meeting Protocol
Team meetings are structured multi-agent discussions involving all four agents, and they are always led by the CEO agent. Meetings are used at key points in the project to synchronize the team, share updates, and plan next steps. The presence of the CEO as a moderator ensures the conversation stays organized and goal-oriented (much like a manager leading a human team meeting). The protocol for meetings is as follows:
Meeting Initiation: The CEO agent decides when to call a meeting. This might be after an initial round of individual work on sub-tasks, or whenever the CEO feels the team needs to regroup (for example, if an unexpected finding needs everyone's input). The CEO sends a meeting call to all agents, possibly including a brief agenda or summary of why the meeting is being held (e.g., "Meeting: review findings on X and decide next steps for Y").
CEO Update: The meeting begins with the CEO agent providing an overview of the current project status. This includes summarizing progress so far, any results that have come in from the agents’ tasks, and the objectives of the meeting. For instance, the CEO might say: "We have gathered a lot of data on Topic X. Researcher found A, Analyst concluded B, Synthesizer has drafted a report. Let's discuss any gaps and finalize our approach for the remaining questions."
Directed Speaking Turns: After the introduction, the CEO will address specific agents one at a time to speak. Only the agent who is addressed should respond, ensuring an orderly discussion. For example, the CEO might say, "@Researcher: Can you update us on the key findings from your web searches?" – The Researcher agent will then present its update to the group (e.g., summarizing sources and what was learned). While the Researcher speaks, the others listen and take notes (their LLM can remember this via mem0). Once the Researcher finishes, the CEO may ask follow-up questions or direct another agent to contribute: "@Analyst: Do these findings make sense, or do we need further investigation?" The Analyst then responds with its analysis perspective.
Interactive Discussion: Although the meeting is moderated, it can still be interactive. The CEO can allow a brief back-and-forth between two agents on a point, but always by explicitly handing the turn. For example, if the Analyst raises a concern about data validity, the CEO might invite the Researcher to clarify that specific point ("@Researcher, please clarify the source reliability for that data"). In this way, the CEO orchestrates a focused dialogue even within the group setting. Agents do not interrupt unprompted; they wait to be called on, which prevents the LLMs from all talking over each other in an uncontrolled way.
Meeting Conclusion: After each relevant agent has given their input and the issues have been discussed, the CEO wraps up the meeting. The CEO will typically summarize the decisions made or the consensus reached (e.g., "Alright team, based on our discussion: we will proceed with strategy X. The Researcher will look into Y, the Analyst will verify Z, and the Synthesizer will prepare the final report draft."). The CEO also outlines any new tasks or changes to assignments that result from the meeting.
Logging: The entire meeting transcript (every message from the CEO and the agents) is recorded in the persistent memory. This log is crucial for posterity – agents can later recall what was said in the meeting if needed. For instance, if the Synthesizer is drafting the final output, it might pull up the meeting transcript from mem0 to ensure it captures the points everyone made. Storing the meeting content also means the system maintains context across multiple meetings; the CEO can refer back to "as we discussed in the last meeting..." and all agents will have access to that context via memory.
Team meetings in Agent Startup serve as checkpoints where the collective intelligence of the group is synchronized. The CEO’s leadership in these meetings reflects a centralized coordination structure, where a central node manages the communication flow
arxiv.org
. This structure is simple and effective for collaboration since one agent (CEO) handles coordination, much like a project manager in a human team. Meetings ensure that all agents are aware of the overall progress and that their efforts remain aligned to the shared goal. They also help in resolving any misunderstandings or misalignments quickly by getting everyone on the same page. After a meeting, the project typically transitions into another round of focused sub-tasks or, if the goal is achieved, into finalization.
Task Assignment and Problem-Solving Workflow (CEO-led)
The overall project workflow is an iterative process orchestrated by the CEO agent to break down and solve the given problem. This can be seen as the “operating procedure” the system follows from the moment it receives a new high-level task to the point it delivers a solution. The workflow involves task decomposition, parallel execution by agents, and integration of results, cycling as necessary. Below is the typical sequence:
Problem Definition: The process starts when a high-level problem or research query is given to the Agent Startup (for example, "Investigate the impacts of technology X on industry Y and suggest potential opportunities"). The CEO agent takes this input and ensures it understands the objective. In this initial phase, the CEO might use its LLM capabilities to rephrase or clarify the problem internally, and it consults the persistent memory to see if any related context from past projects is available (e.g., perhaps a similar research was done before).
Task Decomposition: The CEO agent breaks the overarching problem into smaller, manageable sub-tasks
superannotate.com
. Each sub-task is designed to be tackled by a single agent or a pair of agents. For example, the CEO might identify sub-tasks like: (a) "Researcher: gather data on current trends of technology X in industry Y", (b) "Analyst: analyze the data to identify key impact areas", (c) "Synthesizer: compile a summary of known opportunities from preliminary data". The decomposition is informed by the roles and strengths of the agents as well as the logical structure of the problem. Effective task breakdown is crucial – the CEO ensures that tasks are clear, specific, and collectively cover the scope of the problem.
Agent Assignment: The CEO assigns each sub-task to one or more agents. Typically, tasks are assigned to one agent that is best suited (by role) to handle it. In some cases, the CEO might intentionally assign two agents to collaborate on a sub-task if it requires mixed expertise (e.g., Researcher and Analyst working together on a particularly challenging research that needs both data gathering and immediate analysis). Assignments are communicated via either a direct message (1-1 chat from CEO to that agent with instructions) or announced in a meeting if multiple assignments are given at once. Each assignment includes what is expected and any relevant context or pointers (for instance, the CEO might remind the Researcher to check certain sources, or tell the Analyst what hypothesis to evaluate).
Parallel Task Execution: Once tasks are assigned, the agents work in parallel to execute them. Each agent uses its tools and reasoning to accomplish the sub-task:
The Researcher will perform web searches, read articles, and maybe start a 1-1 chat with the Analyst if clarification is needed on what data is relevant.
The Analyst will begin processing any information available (maybe initial data from memory or from prior tasks) and could ping the Researcher for additional details or the Synthesizer to discuss how findings will be presented.
The Synthesizer might start drafting partial summaries or outlines, and possibly consult the Analyst to ensure the interpretation is correct.
The CEO in this phase mostly observes and waits for results, but can also utilize the time to do a high-level scan of progress (it might check mem0 logs to see what the others are finding, or if it sees any agent is stuck, it could step in to assist or reassign). Essentially, the CEO acts in a supervisory capacity during execution, making sure all agents have what they need.
Throughout this period, some one-on-one chats may occur spontaneously between agents as needed, and all such interactions are recorded. The parallel execution leverages the benefit of multi-agent systems by tackling different aspects of the problem at the same time
superannotate.com
, speeding up the overall process.
Result Collection: As agents complete their sub-tasks, they report back with results. The reporting method can vary:
An agent might send its findings directly to the CEO via a message (e.g., the Researcher shares a list of key statistics and sources).
If multiple agents finish around the same time, the CEO might instead call a short meeting so each can present findings to the group in turn.
Agents also record their findings in the memory (mem0) as they go, so sometimes the CEO can retrieve the results from memory without an explicit report if the protocol defines it.
In any case, the CEO gathers all the sub-task outputs: data points, analyses, partial summaries, etc. At this stage, the CEO evaluates these outputs against the problem objectives. It checks if the pieces together answer the question or if something is missing or inconsistent.
Integration and Analysis: The CEO (possibly with the help of the Synthesizer and Analyst) integrates the individual results into a cohesive understanding of the problem. This might involve the CEO agent itself using its LLM to synthesize an overview from all the inputs, or asking the Synthesizer agent to do so. If the sub-results reveal conflicting information or raise new questions, the CEO notes these issues. For example, perhaps the Researcher found ten points but the Analyst thinks two of them are irrelevant — such discrepancies are identified here. The CEO may do a quick pass to filter out irrelevant findings or highlight particularly important insights to focus on.
Review Meeting: Often, after one cycle of tasks, the CEO will convene a team meeting (as per the Meeting Protocol above) to discuss the findings and decide on next steps. In this meeting, each agent gets to hear what the others did and contribute their opinions on the results. The CEO uses the meeting to verify that everyone’s results make sense collectively and to brainstorm any remaining open questions. It's also an opportunity for agents to propose new ideas now that they see the bigger picture. For instance, the Analyst might suggest an additional analysis that wasn’t originally planned, or the Synthesizer might point out an area that lacks information, prompting further research.
Strategy Update: Based on the outcomes of the tasks and the meeting discussion, the CEO updates the overall strategy. If the problem is fully solved (i.e., the team has gathered enough info and synthesized an answer), the CEO will move to finalizing the output (perhaps instructing the Synthesizer to prepare the final report and having the Analyst verify it). If there are still unanswered aspects, the CEO will plan the next iteration of tasks: possibly breaking down new sub-tasks to tackle remaining issues, or refining existing ones. This may involve assigning follow-up research (e.g., "Researcher, the Analyst identified a gap about topic Z, please find data on that"), or having agents collaborate in a different way (maybe pairing two agents in a chat to figure something out). Notably, as the project progresses, the CEO can utilize the reputation information to assign tasks to the most trusted agents for critical pieces. For example, if one agent has consistently provided high-quality results (and has a high reputation score), the CEO might give that agent a more challenging or central task in the next round.
Iteration: The workflow then loops back to parallel execution of the new tasks, result collection, integration, and further meetings as needed. The process is iterative and continues until the CEO determines that the high-level problem has been resolved to a satisfactory level. Thanks to persistent memory, each iteration builds on the last – agents remember past findings and conversations, which makes subsequent iterations more informed.
Finalization: In the final stage, once the solution is ready, the CEO ensures the Synthesizer produces the polished output (e.g., a written report answering the research question with supporting evidence). The CEO and possibly Analyst review the final output for quality. Then the system can present this result to the user or save it as the project conclusion. A final meeting might be optional just to recap and confirm the solution among the agents themselves.
Throughout this workflow, the CEO agent is the key decision-maker. It acts much like a project manager: planning, delegating, integrating, and adjusting course as necessary
superannotate.com
. The other agents function as specialists who carry out the CEO’s plan and feed their results back into the team. This kind of role-based, iterative coordination is what enables the group to handle complex, abstract tasks systematically
medium.com
superannotate.com
. By dividing the problem and conquering each part through collaboration, the agents collectively reach solutions that might be very hard for a single agent to achieve alone. Importantly, this workflow is flexible – if the nature of the problem changes or if an agent discovers something surprising, the CEO can always re-plan on the fly. The persistent memory and regular meetings make the system adaptive to evolving scenarios, a necessity for tackling real-world research problems

.
Agent Collaboration and Pairing Strategy
In the initial phase of a project, many one-on-one interactions between agents will be set up randomly or by simple rotation. This means the system might pair agents who haven't worked together yet, to encourage knowledge sharing and team bonding. Early on, since no agent has any reputation score or history with others, random pairing ensures each agent gets equal opportunity to interact and form an opinion about the others’ capabilities. For example, the system may randomly schedule a short chat between the Researcher and Synthesizer to discuss initial findings, or between the Analyst and Researcher to verify a particular data point. This helps diversify the communication and avoids siloing in the early stages. As the project progresses, the reputation profiles (built from those post-chat feedback scores) come into play. The system will gradually shift to pairing agents based on who has the highest reputation or best collaborative history:
Agents with high overall reputation scores (meaning they have been rated highly by their peers in past chats) are more likely to be chosen for crucial one-on-one discussions. The assumption is that these agents are contributing valuably and communicating effectively, so putting them together could yield productive outcomes.
Additionally, if there is a particularly strong mutual rapport between two agents (for instance, the Researcher and Analyst consistently give each other 9s and 10s in chats), the CEO or the system may intentionally pair those two for important sub-tasks that require tight collaboration. High mutual ratings indicate a good working chemistry, which the system wants to exploit for efficiency and harmony.
Conversely, if two agents had poor interaction (low ratings), the system might avoid pairing them unless necessary, or the CEO might join or monitor their chat more closely to ensure success.
This evolution from random to reputation-driven pairing is designed to optimize the collaboration network over time. Early random chats gather the data on how well agents work together; later, that data guides the formation of effective teams. It’s analogous to how in a human workplace, initially team members might be randomly assigned to work together, but as a manager learns who works well with whom, they might pair those people on critical tasks. By the end of a project (or in subsequent projects, since agents persist), the system has a refined sense of the team dynamics and can automatically utilize the best pairings for problem-solving. It's important to note that the CEO agent remains the central coordinator, so it will often be involved in or aware of any pairing decisions. The CEO might explicitly instruct two agents to have a direct chat on a topic, taking into account their reputation scores. In all cases, the goal is to balance giving everyone a chance to contribute with leveraging the most successful collaborations to solve the problem efficiently.
Memory and Reputation System
A standout feature of Agent Startup is its persistent memory and reputation tracking, which together enable learning and adaptation over time. This section describes how mem0 is used to store knowledge and context, and how the reputation profiles are maintained and utilized.
Persistent Shared Memory (mem0)
All agents in the system share a common long-term memory storage, referred to as mem0. This memory is the cumulative "experience" of the agents across all interactions and sessions
medium.com
. In practice, mem0 is implemented using a specialized memory framework that supports both short-term context and long-term storage (for example, using a vector database for semantic recall and a graph or document store for factual recall
medium.com
). The key characteristics of mem0 in our design are:
Universality: Everything that the agents read, say, or otherwise encounter is saved into mem0. This includes:
Transcripts of one-on-one chats (tagged with which agents were involved and the timestamp).
Transcripts of team meetings (with speaker labels for each utterance).
Web content that agents fetch (e.g., if the Researcher reads a web page, the relevant text and URL can be stored).
Task results and reports (any final outputs or intermediate write-ups by agents).
Essentially, mem0 acts as an ever-growing knowledge base of the project. By having a single shared memory, we ensure all agents operate on a common ground of knowledge. For instance, the Synthesizer doesn’t only rely on what it personally heard in a meeting; it can directly query mem0 for details from the Researcher's search results.
Persistence: mem0 is not wiped when a session ends. If the Agent Startup system is stopped and restarted, mem0 reloads the stored data, so the agents remember past projects. This allows knowledge to accumulate over multiple projects (if they are related or if past solutions can inform new ones). It also means that if the user comes back later with a follow-up question, the agents don't start from scratch—they have the entire history of what was done before. This persistent context is exactly what mem0 is designed for
medium.com
, avoiding the stateless nature of typical LLM sessions. Over time, the agents could build up a rich repository of research across domains.
Memory Management: Because mem0 grows with each interaction, it could become very large. The system will employ strategies to manage this:
Indexing and Search: Using vector embeddings, agents can perform semantic searches over mem0 to find relevant information quickly. For example, if the Analyst recalls that a similar issue was discussed in a prior meeting, it can search mem0 by keywords or semantic similarity to retrieve that snippet, rather than reading the entire log.
Summarization: For very long histories, the system can periodically summarize older memory entries. Summaries of past conversations or results can replace verbatim logs after they are no longer immediately needed, to save space and improve retrieval times. The important details remain as distilled notes.
Structured Storage: Important data extracted during the project (key facts, figures, decisions) can be stored in a structured way (e.g., as JSON entries or graph nodes within mem0) so that agents can query specific fields (like "what was the final decision on topic X?") without parsing raw text.
Access Control: Generally, all agents can read from mem0 freely. Writing to mem0 is done automatically by the system for all communications, but agents can also programmatically add notes to memory if needed (for instance, an agent might save a conclusion it reached in mem0 as a separate note for emphasis). One nuance: while all agents have access to the same pool of information, they might not always use all of it unless relevant. Each agent still decides (through its prompt and design) what to pay attention to. The CEO, for example, might utilize memory broadly to recall anything that might affect planning, whereas the Researcher might mostly look at memory for any prior related research results when starting a new search task.
Mem0 essentially provides the collective memory for the agent startup. It is like a shared brain that retains the context of the problem and the team’s knowledge. This greatly enhances collaboration, as one agent can benefit from another’s past work without direct communication. It also enables continuity: the system feels like a persistent team that learns over time, rather than a fresh AI instance for each query. In line with research on LLM-based agents with long-term memory, this persistent context allows more complex, coherent behavior over prolonged tasks
medium.com
. We will leverage mem0’s capabilities fully to ensure no information is lost and the agents can always build on all available knowledge.
Reputation Profiles and Scoring
In order to improve teamwork and optimize agent interactions, Agent Startup implements a reputation system for the agents. Each agent has a reputation profile that reflects how positively they are perceived by their peers based on past one-on-one chats. The main components and functioning of this system are:
Interaction Scoring: As described in the 1-1 Chat Protocol, after every private chat between two agents, both participants provide a score from 1 to 10 evaluating the interaction quality of the other. This score is essentially a peer review – did the other agent contribute meaningfully, communicate clearly, and cooperate well? Higher scores indicate a better experience. These scores are provided immediately after the chat and are kept private (agents do not see the numeric ratings they receive, to avoid biases or conflict; the scores are used by the system for internal adjustments).
Profile Data: Each agent’s reputation profile stores all the ratings they have received from others. We can store this as a simple list of scores or as an aggregate. A straightforward approach is to maintain an average reputation score for each agent that updates with each new rating. For example, if Agent 2 (Researcher) has had three chats and got scores 8, 9, and 7, their average reputation might be 8.0. We could also maintain more detailed data, like separate averages per partner (maybe Agent 2 averages 9 from the Analyst but 7 from the Synthesizer, indicating something about those pair dynamics). In early implementation, a global average or median will suffice as the reputation metric.
Use of Reputation: The system uses these reputation profiles to influence future collaboration in a few ways:
Pairing: When scheduling or suggesting one-on-one chats, the system prefers pairing agents with higher reputation scores (especially as tasks get critical). As noted, in later stages of a project, we lean towards high-rep pairs to maximize productivity. If Agent 3 (Analyst) and Agent 4 (Synthesizer) both have the highest rep scores in the team, the system might allocate them to work together on a challenging sub-problem, expecting a fruitful collaboration. Reputation thus helps identify the strongest contributors and encourages their direct interaction.
Task Assignment: The CEO agent can factor in reputation when assigning tasks. For instance, if a particular agent has a low reputation (maybe they had trouble communicating or delivering in earlier chats), the CEO might assign them a smaller or less critical task to avoid bottlenecks, while giving high-rep agents more responsibility. On the flip side, if an agent has a stellar reputation, the CEO might trust them with the most complex research task or ask them to double-check others' work.
Mentorship: If an agent is consistently rated low by others, the CEO might intervene by pairing that agent with a high-performing agent in a chat or small meeting to help improve them (sort of a mentorship scenario). The reputation system can thus highlight which agents need more coordination or guidance.
Reputation Update Cycle: We will update each agent’s reputation profile immediately after each rating is given. This could be done by the system process that handles the end of chats. The updated reputation scores are stored (potentially also in mem0 or a separate profile registry). These profiles persist across sessions too – meaning an agent carries its reputation from one project to the next. Over a long term, this could shape roles (for example, an agent that consistently shines might effectively become the "go-to expert" in the team). It also means the system can learn which agents might need replacement or reconfiguration if their reputation remains poor (though initially we keep the same four agents, we could consider retraining or adjusting prompts for a low-rep agent as a form of improvement).
Calibration: We’ll encourage agents to use the full 1–10 scale and calibrate their scoring roughly around a common standard (likely communicated in their system prompt, e.g., "10 = extremely helpful, 5 = average, 1 = detrimental"). This ensures the scores are meaningful and comparable. Since all agents are clones in terms of code (just different roles), they should have a consistent understanding of the rating scale as instructed.
The reputation profile mechanism introduces a feedback loop in the multi-agent system. It’s inspired by how human teams build trust and how performance reviews can improve team allocation. By quantifying the quality of interactions, the system can adapt to use the best teamwork dynamics available

. This is especially important in a persistent system—over time, the difference between a well-coordinated agent pair and a poor one can greatly affect efficiency and success. The reputation system allows the Agent Startup to learn from its own teamwork experience and self-optimize its collaboration patterns. We expect this to lead to an overall improvement in problem-solving capability as the agents effectively "trust" and rely on each other in more informed ways as they accumulate shared history.
Extensibility and Future Improvements
The Agent Startup project is designed with extensibility in mind. As we build the initial system with four agents and the features described, we are also considering how it could be expanded or improved in the future to handle even more complex tasks or different use cases. Here are several areas of potential extension:
Scaling the Number of Agents: While the current design uses four agents with fixed roles, we can add more agents or vary the team composition for different projects. For example, if a task requires a specific type of expertise (say legal research or coding), we could introduce a new agent specialized in that area. The system could be made to handle dynamic agent pools, where agents can join or leave a project. We might also explore a hierarchy of agents: if the problem is very large, there could be multiple "sub-teams" each with their own coordinator agent, all overseen by a top-level coordinator (an extension of the CEO concept). This hierarchical MAS approach could tackle tasks that are too big for one team by splitting work across teams.
Additional Tools and Skills: Currently, internet search is the primary external tool. In the future, we can equip agents with more tools to broaden the scope of tasks they can handle. Possibilities include:
A calculator or code execution tool for the Analyst agent, to allow solving math problems or running simulations.
A document parser to let the Researcher upload and analyze local PDFs or datasets (beyond just web content).
An API integration tool, so agents can fetch data from specific services (e.g., financial data APIs, scientific databases) as part of research.
A knowledge-base lookup for internal use, if we have a corpus of proprietary data.
PydanticAI’s framework makes it straightforward to add such function tools that the agents can call
ai.pydantic.dev
. Introducing new tools will likely come with adjusting the agent prompts so they know when and how to use them. This extension would enhance the system's problem-solving versatility.
Enhanced Memory Management: As projects accumulate, mem0 will contain a vast amount of information. We may need to implement more advanced memory management strategies:
Memory Segmentation: Partition mem0 by project or topic, so agents don’t confuse contexts between unrelated projects. For example, have a project-specific memory that links to a global memory for general knowledge.
LTM Summarization Agents: Introduce a background process or a dedicated "Librarian" agent whose job is to maintain the memory database – summarizing long-past events, merging duplicate information, and highlighting key learnings. This agent could occasionally review mem0 and produce a concise knowledge base for the team.
Contextual Memory Retrieval: Use techniques to automatically fetch the most relevant memory snippets into an agent’s context window when it’s working on a task. This could be through semantic search triggers or via the agent asking a memory tool. The goal is to cope with LLM context window limits by intelligently selecting what part of the huge memory to use at any time.
Improved Reputation System: The current reputation scoring is a simple 1–10 feedback after chats. We could extend this in several ways:
Multi-faceted Reputation: Track different dimensions such as expertise, communication, and cooperativeness separately. An agent might be very knowledgeable (high expertise score) but maybe not as good at listening (lower communication score). This granularity could help the CEO assign tasks even more smartly (e.g., pair a highly cooperative agent with a highly expert but less cooperative one to balance).
Reputation Decay: Implement a decay factor so that older scores matter less over time, ensuring the reputation reflects recent behavior more. This way, an agent can improve from a bad start or needs to continuously perform well to maintain a high reputation.
Integration with LLM Behavior: Use the reputation as part of the agent's prompt context – for example, an agent could be aware of its own standing or others' standing. This could encourage, say, a low-rep agent to try harder (though we must be careful; it might also induce undesired biases, so this would be experimental).
Peer Feedback Discussion: Allow agents to optionally give qualitative feedback to each other or discuss the collaboration in a reflection phase. This could help identify issues (maybe the Synthesizer can tell the Researcher "I had trouble using your data because X was missing"). Such feedback could either be processed by the system or even by the agents themselves to adjust their behavior in future interactions.
Learning and Adaptation: Since the agents and memory persist, we have an opportunity to continuously improve the agents. Future enhancements might involve:
Prompt Tuning: After several projects, analyze where agents struggled or made mistakes (we will have transcripts for analysis). We can refine the agents’ system prompts or examples to correct those patterns. For instance, if the Analyst agent often overlooks certain details, update its instructions to always check for those.
Model Updates: Swap in newer or specialized LLM models for certain agents as needed. If a domain-specific model (like a medical domain LLM) becomes available, we could use it for an agent when tackling a related project.
Automated Workflow Adjustments: Use meta-learning to let the system adjust parameters like the chat message cap or meeting frequency based on what’s effective. For example, if 30 messages in 1-1 chat is consistently too low or too high, the system could learn to change it.
User Interaction and Transparency: In the future, we might add a way for a human user or overseer to interact with the Agent Startup during a project. This could mean:
The user can ask for status updates or join the meeting (as an observer or participant).
The system could generate a log or dashboard from mem0 to show the reasoning steps and sources gathered (helpful for verifying the final answer).
If something goes wrong (agents get stuck or go off track), a human could intervene by adjusting a task or correcting a piece of information. Designing for such interventions could be valuable for practical deployments.
Broader Collaboration Modes: We primarily implemented a cooperative team with a centralized leader (the CEO). Extensibility could include exploring other collaboration structures:
Decentralized teamwork where agents self-organize without a single leader, which would require more complex negotiation protocols between agents.
Competitive agents where two agents might be tasked with producing alternative solutions (introducing a bit of competition and then a selection mechanism to choose the best outcome, perhaps decided by the CEO or a voting system).
Specialized meeting types like brainstorming sessions where agents can speak more freely without turn-taking, under some moderated rules, to generate creative ideas.
Domain Adaptation: While "internet research tasks" are the initial focus, the platform could be adapted to other domains. For instance, an Agent Startup variant could be used for software development (with agents like a Planner, Coder, Tester, etc.), or for business decision support (with agents like Market Analyst, Financial Analyst, Risk Assessor, etc.). The plan and architecture largely remain the same, but the agent roles, tools, and knowledge base would change. This shows the design is fairly general: the concept of persistent, collaborating AI agents with memory can be applied to many complex problem domains.
